1. Requirement vs. Specification & 功能/非功能需求 Tutorial 5
Requirement (需求) = 利益相關者的需要 (What)；Specification (規格) = 技術分析文檔，描述特徵與行為 (How)。Functional (功能需求) 用動詞 (Verbs) 描述系統必須做什麼；Non-functional (非功能需求) 用形容詞/副詞描述系統品質（Look & feel, Usability, Performance, Operational, Security）。
2. Design Thinking 五階段與 UI vs. UX Tutorial 6
UI 關注視覺與交互元素美感；UX 關注整體無縫且有意義的體驗。Stanford d.school 設計思維 5 階段：Empathize (共情) ➔ Define (定義問題/Personas) ➔ Ideate (構思) ➔ Prototype (低成本原型) ➔ Test (測試)——這是一個非線性、迭代 (Non-linear, iterative) 的過程，專治 Ill-defined / Wicked problems！
3. Feedback (反饋) vs. Constraints (約束) Tutorial 7.0
Feedback = 系統對用戶動作的直接回應（消除「我點到了嗎？」的不確定感，且報錯必須緊挨著出錯欄位！）。Constraints = 限制與防呆規則（如灰顯不可用選單、PS/2 顏色防呆、播放器帶豎線的跳到首尾圖標 |◁ vs ▷|），防止用戶犯錯。
4. 對話三層次定位法与 STN 單一 Escape 弧 Tutorial 7.1 & 7.2 官方答案
評分標準 (Marking Point)：「問題出在哪裡？」Shape/外觀 = LEXICAL；Sequence/順序 = SYNTACTIC；Effect on data/數據效果 = SEMANTIC。在 STN 中將 Cancel 畫成單一共享 Escape 弧，是為了避免每個狀態重複畫線導致變成意大利麵條圖 (Spaghetti of duplicated behaviour)！
5. Steve Krug《Don't Make Me Think》三大用戶真相 Tutorial 8
① We don't read pages, we SCAN them（用戶在執行任務，只掃視感興趣的碎片）；② We don't make optimal choices, we SATISFICE（匆忙中選第一個「足夠好」的合理選項，猜測更快更好玩）；③ We don't figure out how things work, we MUDDLE THROUGH（只要能用就將就用，不在乎底層原理）。
6. Maze 原型測試三大路徑指標與信息架構測試 Tutorial 3
① Direct Success (直接成功)：按預期路徑完成任務；② Indirect Success (間接成功)：走了非預期繞路但最終到達終點屏；③ Give-up / Bounce (放棄/跳出)：中途離開未完成。外加 Card Sort (卡片分類) 與 Tree Test (樹測試：檢驗層級導航共識)。

🔍 2. 需求收集方法與 PACT 框架 (Page 4)

  • 設計系統前必須搞清的 7 個問題：誰用 (Who)？在哪用 (Where)？用來做什麼 (What for)？怎麼用 (How)？什麼會降低用戶效率？什麼會降低你設計的效率？相關人員有什麼隱藏或公開的議程 (Agendas)？

  • 🔥 必背縮寫：PACT Analysis = People (人) + Activity (活動) + Context (語境/環境) + Technology (技術)！

📐 3. Usability / UI Specifications (界面規格書四要素, Pages 5-8)

呼應 Lecture 02：當問題具備完整規範 (Full specification) 時就是 Well-defined problem。UI Spec 是設計界面的藍圖與模板，包含 4 大要素：

  • 1. Visual overview of the screen：將屏幕拆分為多個區塊 (Sections)，並在文檔中為每個區塊建立對應章節。
  • 2. Display rules within each section：每個區塊內的顯示規則（例如搜尋結果如何排序？顯示哪些欄位？某欄位缺失時怎麼辦？）。
  • 3. Consider messaging：在特定條件下要顯示什麼特定提示訊息？
  • 4. Evaluate the links：每個連結跳轉到哪個頁面是否顯而易見？若不明顯必須明確指定。

🧭 4. Tutorial 3 考點提煉：Maze 可用性測試指標

在原型可用性測試中，分析結果有兩種維度：By block (按任務塊) 與 By tester (按測試者全流程 Session)。核心指標包括：

  • Direct Success (直接成功)：測試者沿著你設定的預期路徑 (Expected path) 完成任務。
  • Indirect Success (間接成功)：測試者走了非預期路徑 (Unexpected path / Off-path) 繞了彎路，但最終仍到達了終點界面。
  • Give-up / Bounce (放棄 / 跳出)：測試者中途離開或放棄，未能完成任務。
  • Card Sort (卡片分類塊)：查看多少百分比與唯一數量的用戶將某張卡片歸入你定義的分類中。
  • Tree Test (樹測試塊)：查看最受歡迎的最終分類 (End screen) 與最常見層級路徑 (Most common paths)，判斷用戶對內容分類與導航是否存在共識 (Consensus)。

💡 Tutorial 6: Design Thinking (設計思維 5 階段) 與 UI vs. UX Week 6.1

🎨 UI Design vs. UX Design (Page 1 框線重點)

  • UI Design (用戶界面設計)：聚焦於產品的視覺與交互元素 (Visual, interactive elements)，以打造賞心悅目的界面 (Aesthetically pleasing interfaces)。
  • UX Design (用戶體驗設計)：聚焦於透過理解用戶需求、開展調研並設計直觀界面，創造無縫且有意義的用戶體驗 (Seamless and meaningful user experience)。

🔄 為什麼需要 Design Thinking？(Pages 1-2)

  • 核心定義：設計思維是一個非線性、迭代的過程 (Non-linear, iterative process)，最擅長解決定義不良或未知的問題 (Ill-defined / unknown / wicked problems)！
  • 作用：以人為中心重構問題 (Reframe in human-centric ways)，是「跳出思維定勢 (Thinking outside the box)」的最佳方法。各階段常並行、亂序並反覆迭代執行。

🛡️ Tutorial 7.0: Feedback (反饋)、Constraints (約束) 與有限狀態機 (FSM) Week 7 Part 1

📢 1. What is Feedback? (什麼是反饋, Pages 1-2)

  • 系統對用戶動作的直接反應或回應（界面與用戶對話，告知當前發生了什麼，並指引下一步如何正確完成任務）。
  • 核心心理作用：消除用戶的「這東西管用嗎？我剛才按到按鈕了嗎？表單提交成功了嗎？」等不確定感與焦慮，帶來安心感 (Peace of mind，如 Blackboard 提交作業後的綠色確認橫幅與回執編號)。

🚧 2. What are Constraints? (什麼是約束, Pages 2-5)

  • 限制或規則 (Limit or restriction)。好的約束能防止用戶犯錯（防止輸錯數據、按錯按鈕、選錯選項）。
  • 講義 7 大約束+反饋實例 (Pages 4-5)：① 刪除文件確認彈窗；② 手機連電腦的提示音 + USB 傳輸模式單選約束（不選 File Transfer 就不能傳文件）；③ 風扇調速旋鈕（圓圈指示 1~4 檔，限制最高只能轉到 4 檔）；④ 筆電充電蜂鳴與 100% 上限約束；⑤ 定位權限 3 選 1 約束（Only this time / While using / Deny）；⑥ 冰箱季節溫度檔位約束（冬1-3 / 雨季3-5 / 夏5-7）；⑦ 紅綠燈 3 種約束（紅停、綠行、黃準備停）。

🏛️ Part 1: 圖書館自助機 (Library Self-Service Kiosk) — 對話三層次診斷 (10 min)

🎯 官方評分鐵律 (Marking Point)："The level answers 'where is the problem located' — shape (LEXICAL), sequence (SYNTACTIC), or effect (SEMANTIC)." 點擊下方 a, b, c 三道題查看官方標準答案：

a) The “Confirm” button is round and green; the “Cancel” button is square and grey.

✅ LEXICAL (詞法層) — It is about the physical shape and appearance of the controls (round/green vs. square/grey).

b) The kiosk asks for payment BEFORE letting the user choose which books to renew, and users keep tapping back.

✅ SYNTACTIC (句法層) — It is about the wrong ORDER (先後順序) of inputs and outputs in the conversation; every tap itself “works”.

c) Pressing “Renew all” silently renews three books that were reserved by another user – the tap was fine, the effect was wrong.

✅ SEMANTIC (語義層) — Input and order were correct, but the effect on the application's data was wrong (reserved books got renewed).

🔐 Part 2: 繪製 Login Dialog 的 STN 模型與「單一 Escape 弧」必考問答 (10 min)

題目要求：系統打開在 Welcome 界面；用戶選擇 “Log in”，在 Login form 輸入憑證並按 Submit。若密碼有效則結束於 Logged in；若無效則顯示錯誤並返回 Login form。“Cancel” 逃生弧可從登錄對話框內任意位置返回 Welcome。

🔥 必背一行簡答題：Why is the escape drawn as one arc rather than on every state?
✅ 官方滿分答案 (Tutorial 7.2 Page 1)："Without it, every state needs its own identical Cancel arc – the diagram turns into spaghetti of duplicated behaviour; a single shared escape (like a Help menu at meta level) keeps the model readable."

🧠 Tutorial 8: Usability by Examples — Steve Krug《Don't Make Me Think》 Week 8

核心法則：糟糕的 UI 設計就像「把你扔在沙漠中央，指望你自己走出去 (Drops you off in the middle of the desert)」。一個好的網頁或 App 應該是不言自明、顯而易見、自我解釋的 (Self-evident, obvious, and self-explanatory)——目標是消滅用戶腦子裡所有的問號 (Get rid of question marks)！

❓ 1. 讓用戶思考的 6 件事 (Page 2)

  • 1. Cute or clever names (自作聰明的花哨名稱，如把求職叫 Job-o-Rama)
  • 2. Marketing-induced names (營銷造詞)
  • 3. Company-specific names (公司內部黑話)
  • 4. Unfamiliar technical terms (生僻技術術語)
  • 5. Too much information (信息過載)
  • 6. Not clear links (看不出能不能點的連結)
求職按鈕對比：[Jobs] (0思考，直接點) > [Employment Opportunities] (幾毫秒思考) > [Job-o-Rama] (滿頭問號)！

👀 2. 用戶如何真正使用 UI？(Pages 5-7)

  • 真相 1：We don't read pages, we SCAN them (只掃視不閱讀)。為什麼？① 我們在執行任務 (On a mission)，趕時間；② 知道不必讀完所有內容，只找感興趣的碎片；③ 我們很擅長掃視。
  • 真相 2：We don't make optimal choices (不找最優解，只找滿意解 Satisficing)。為什麼？① 趕時間；② 選錯幾乎沒懲罰 (點 Back 就行)；③ 權衡選項未必更好；④ 猜測更有趣且更快！
  • 真相 3：We don't figure out how things work, we MUDDLE THROUGH (將就湊合用)。只要能用就不在乎原理；一旦找到一個能用的笨辦法就會一直用下去。

🏛️ 3. 慣例與有效視覺層次 (Pages 7-11)

  • Conventions are your friends (慣例是你的朋友)：① 位置慣例（Logo 在左上角，主導航在頂部或左側）；② 工作方式慣例（電商購物車隱喻）；③ 外觀慣例（標準化視頻/社交圖標）。
  • Effective Visual Hierarchy (有效視覺層次 3 大特徵)：
    1. 越重要的東西越突出 (More important = more prominent)；
    2. 邏輯相關的東西在視覺上也相關 (Related logically = related visually)；
    3. 視覺嵌套顯示從屬關係 (Nested visually to show what's part of what)。

✈️ 案例對比 1：機票搜尋 BOS vs. NY 與路邊停車牌重构 (Pages 3 - 4)

• 壞設計 (Page 3)：用戶在出發地輸入 bos，下拉選單貼心彈出 Boston, MA, US (BOS)，選中後框裡卻只剩代碼 BOS；接著用戶以為系統很聰明，在目的地輸入 ny 並直接點搜尋，系統卻報錯：Please enter a valid 'TO' City or Airport code（因為紐約有 JFK/LGA/EWR 多個機場，沒有 NY 這個機場代碼，違反了一致性與容錯）！
• 好設計 (Page 4)：輸入 ny 時自動展開下拉選單列出 NYC - New York City (Area) 等所有匹配項，且選中後完整顯示 BOS - Boston Logan Inter！
• 路邊停車牌重构 (Page 4 下圖)：將原本4塊上下堆疊、充滿文字邏輯計算的告示牌，重構為一張「星期 × 時間軸」的紅綠網格時間表 (Parking Schedule Grid)，一眼就能掃視 (Scan) 出現在能不能免費停車！

📐 案例對比 2：有缺陷的視覺層次 (Flawed Visual Hierarchy) 與排版掃視法則 (Pages 9 - 11)

• Flawed VH (橫跨錯誤的標題欄, Page 10)：如果把黑底標題欄 Computer Books 畫得橫跨左邊的導航欄 (Books, Music, Movies, Games) 和右邊的主內容區，會在視覺嵌套上誤導用戶以為「Music 和 Movies 也屬於 Computer Books 的子分類」！正確做法：標題欄只橫跨右側它真正統轄的主內容區！
• 支持掃視 (Support Scanning) 的排版鐵律 (Page 11)：
1. 大量使用標題 (Use plenty of headings)，且不要讓標題懸浮 (Don't let heading float — 標題離它引出的正文距離，必須小於離上一段結尾的距離)；
2. 保持段落簡短 (Keep paragraphs short)；
3. 使用項目符號列表 (Use bulleted lists，且列表項之間要留出適當行距，不要擠成一團)；
